## 🎯 Definition

**TLS (Transport Layer Security)** is a cryptographic protocol that secures communication over a network by providing **confidentiality** (encryption), **integrity** (tampering detection), and optionally **authentication** (server and sometimes client identity via certificates). It runs above TCP and below application protocols such as HTTP, SMTP, or IMAP.

**Origin:**
- **SSL (Secure Sockets Layer)** – Netscape, 1990s; SSL 2.0/3.0 are **deprecated** and insecure.
- **TLS 1.0** (1999) → **TLS 1.1** (2006) → **TLS 1.2** (2008) → **TLS 1.3** (2018). Today use **TLS 1.2** or **TLS 1.3** only.
- TLS is specified in RFCs (e.g. 5246 for 1.2, 8446 for 1.3) and is the basis of **HTTPS**.

**Key Principle:**
> "Encrypt and authenticate the pipe so that eavesdroppers cannot read the data and attackers cannot alter it without detection."

**Alternative formulation:**
> "TLS turns an untrusted network into a private, tamper-evident channel between two endpoints, so applications can send passwords, tokens, and API keys without exposing them on the wire."

## 🏗️ The Three Guarantees

```
┌─────────────────────────────────────────────────────────────────┐
│  WITHOUT TLS                                                     │
│                                                                  │
│  Client ◄────── plaintext (readable, modifiable) ──────► Server  │
│           ❌ Eavesdropping  ❌ Tampering  ❌ Impersonation        │
└─────────────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────────────┐
│  WITH TLS                                                        │
│                                                                  │
│  Client ◄────── ciphertext + MAC / AEAD ──────► Server           │
│           ✅ Confidentiality  ✅ Integrity  ✅ Authentication    │
│              (encryption)     (tamper-proof)   (certificates)    │
└─────────────────────────────────────────────────────────────────┘
```

| Guarantee | Meaning |
|-----------|---------|
| **Confidentiality** | Only the intended peer can read the data; everyone else sees ciphertext. |
| **Integrity** | Any change to the data is detected (MAC or AEAD); tampered segments are rejected. |
| **Authentication** | The server (and optionally the client) proves identity using a certificate and private key. |

## 📦 Core Concepts

### Handshake (Simplified)

The handshake establishes a shared secret and optionally verifies the server’s certificate.

**TLS 1.2 (classic):**
1. Client sends **ClientHello** (supported versions, ciphersuites, extensions).
2. Server responds **ServerHello** (chosen version, ciphersuite), **Certificate** (server cert chain), **ServerKeyExchange** (if needed), **ServerHelloDone**.
3. Client verifies the certificate (signature, chain, expiry, hostname).
4. Client sends **ClientKeyExchange** (encrypted premaster secret or DH params).
5. Both derive the **master secret** and **session keys** from premaster + random values.
6. **ChangeCipherSpec** + **Finished** (first encrypted message; verifies handshake integrity).

**TLS 1.3:** Fewer round-trips, removed weak ciphers and options (e.g. static RSA key exchange), 1-RTT by default (and 0-RTT optional). Prefer 1.3 when both sides support it.

### Cipher Suites

A ciphersuite names: key exchange, authentication, bulk cipher, and MAC (or AEAD).

Examples:
- **TLS 1.2:** `TLS_ECDHE_RSA_WITH_AES_128_GCM_SHA256` – ECDHE key exchange, RSA in cert, AES-128-GCM, SHA256.
- **TLS 1.3:** Suites are AEAD-only (e.g. `TLS_AES_128_GCM_SHA256`). Key exchange is always (EC)DHE; authentication is RSA or ECDSA in the certificate.

**Best practice:** Prefer **TLS 1.3** or **TLS 1.2** with forward-secret key exchange (ECDHE/DHE) and strong AEAD (e.g. AES-GCM). Disable SSL and TLS 1.0/1.1.

### Certificates and Authentication

- The server sends a **certificate** (and chain). The certificate binds a **public key** to a **name** (e.g. `api.example.com`) and is signed by a **Certificate Authority (CA)**.
- The client (or OS/browser) has a **trust store** of CA roots. If the chain leads to a trusted CA and the name matches (and the cert is valid and not revoked), the client trusts the server’s public key.
- **Client authentication** (mutual TLS, mTLS): the client also has a certificate; the server verifies it the same way. Used in service-to-service or high-assurance scenarios.

## 🔄 TLS and HTTPS

**HTTPS** = HTTP over TLS. The application speaks HTTP; TLS provides the secure layer below.

- **Port:** Typically **443** (HTTP uses 80).
- **URL:** `https://` triggers TLS before any HTTP request.
- **Hostname verification:** The client checks that the server’s certificate **Subject Alternative Name (SAN)** or **Common Name (CN)** matches the host (e.g. `https://api.example.com` → cert must be for `api.example.com`). Never disable hostname verification in production.

OAuth 2.0, JWT, and most security standards **require HTTPS** so tokens and credentials are not sent in cleartext.

## 💻 Practical Notes

### Checking a Server’s TLS Configuration

```bash
# Check supported protocols and ciphers (example: OpenSSL)
openssl s_client -connect api.example.com:443 -servername api.example.com

# TLS 1.2 only
openssl s_client -connect api.example.com:443 -tls1_2

# TLS 1.3 only
openssl s_client -connect api.example.com:443 -tls1_3
```

### Configuring TLS (Conceptual)

- **Server:** Configure a valid certificate (from a public CA or internal CA), private key, and supported protocols (e.g. 1.2, 1.3) and ciphersuites. Disable SSL and TLS 1.0/1.1.
- **Client:** Use default trust store (OS or runtime); for mTLS, provide client certificate and key. Always verify server certificate and hostname.

### Node.js (HTTPS client)

```javascript
const https = require('https');

// Uses system CA store by default; verifies server cert and hostname
https.get('https://api.example.com/data', (res) => {
  console.log(res.statusCode);
  res.on('data', (chunk) => { /* ... */ });
}).on('error', (err) => console.error(err));
```

### Python (requests)

```python
import requests

# Verifies server cert and hostname by default
r = requests.get('https://api.example.com/data')
# For custom CA or mTLS: verify='/path/to/ca.pem', cert=('client.crt', 'client.key')
```

## 🔐 Security Considerations

| Topic | Recommendation |
|-------|----------------|
| **Protocols** | Use TLS 1.2 or 1.3 only; disable SSL, TLS 1.0, 1.1. |
| **Forward secrecy** | Prefer (EC)DHE so past traffic is not compromised if long-term keys leak. |
| **Certificates** | Valid chain, not expired, correct hostname; check revocation (CRL/OCSP) where required. |
| **Hostname** | Always verify server identity (SAN/CN) against the host you connect to. |
| **Private keys** | Keep server (and client) private keys secure; restrict permissions; use HSM where appropriate. |
| **Cipher suites** | Prefer AEAD (e.g. AES-GCM); avoid NULL, export, or weak ciphers. |

## 📊 When to Use TLS

| Scenario | Use TLS? |
|----------|----------|
| Any HTTP API (REST, GraphQL) in production | ✅ HTTPS (TLS) required |
| OAuth 2.0 / OIDC / JWT in production | ✅ TLS required |
| Internal service-to-service | ✅ Prefer TLS (often with mTLS or VPN) |
| Local dev (localhost) | ⚠️ Optional; use TLS for production-like testing |
| Legacy internal protocols | ⚠️ Prefer wrapping in TLS or moving to TLS-capable protocols |

---

## ⚠️ Common Pitfalls

1. **Disabling certificate or hostname verification** – “For testing only” often leaks to production; never disable in prod.
2. **Using SSL or TLS 1.0/1.1** – Insecure; use TLS 1.2+ only.
3. **Wrong hostname in cert** – Cert must match the host (e.g. SAN/CN); avoid using one cert for many unrelated names unless it’s a wildcard and policy allows.
4. **Expired or revoked certificates** – Monitor expiry and revocation; renew before expiry.
5. **Weak ciphers or no forward secrecy** – Prefer TLS 1.3 or 1.2 with ECDHE/DHE and strong AEAD.

---

## 🎯 Best Practices

1. **TLS 1.2 or 1.3 only** – Disable older protocols and weak ciphers.
2. **Valid certificates** – Use a trusted CA (public or internal); keep chains complete and up to date.
3. **Hostname verification** – Always on for clients; never skip for production.
4. **HSTS** – Use HTTP Strict Transport Security so browsers use HTTPS only.
5. **Monitor** – Expiry, revocation, and configuration (e.g. SSL Labs style checks).

| Topic | Relationship |
|-------|--------------|
| **JWT / OAuth 2.0** | Tokens and credentials must be sent over HTTPS (TLS). |
| **Certificate Chains / PKI** | TLS server (and mTLS client) authentication relies on certificate chains and CAs. |
| **Public-Key Cryptography** | Certificates contain public keys; key exchange and signatures use asymmetric crypto. |
| **API Gateway** | Often terminates TLS at the edge and forwards to backends over TLS or internal network. |

---

## 📝 Key Takeaways

1. **TLS** provides **confidentiality**, **integrity**, and **authentication** for data in transit; use TLS 1.2 or 1.3 only.
2. **HTTPS** is HTTP over TLS; use it for all production APIs and auth flows.
3. **Certificates** bind a public key to a name and are signed by a CA; clients verify the chain and hostname.
4. **Handshake** agrees version, ciphersuite, and keys; then application data is encrypted and integrity-protected.
5. **Never** disable certificate or hostname verification in production; prefer forward secrecy and strong ciphers.
